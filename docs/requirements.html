1

Purpose

A driver signs up on their phone, uploads their documents and their vehicle, and waits while a compliance team checks them. This backend runs that process end to end: it holds the application, decides when it is complete enough to submit, and carries the verification result back to the driver.

It is a backend only. It serves JSON and renders nothing. The driver app and the admin panel are separate products built against it.

Why this document exists. An earlier build followed a ten-endpoint sketch that turned out narrower than the screens. Two whole screens had no endpoint behind them, and the submitted screen expected a shape the API did not return. This document starts from the screens instead, so that gap cannot open again.

Architecture

Modular and layered, with dependencies pointing inward only. A service names an interface, never a concrete class; one file binds the two.

src/
  main.ts            listen
  app.ts             express app, middleware order
  container.ts       the only file naming both an interface and a class
  common/
    errors/          the one error type services throw
    http/            response envelope, error handler, async wrapper
  modules/
    <feature>/
      *.types.ts       the contract
      ports/           interfaces the service depends on
      providers/       implementations behind those interfaces
      *.service.ts     business rules
      *.controller.ts  HTTP in, HTTP out
      *.routes.ts      the router
IDRequirement
ARC-1A controller performs no business logic. It validates input, calls one service, returns the result.
ARC-2A service imports no Express type and no concrete repository. Collaborators arrive through its constructor.
ARC-3Persistence sits behind an interface. Swapping the store must not change a service.
ARC-4Values that vary by market — document lists, colours, age limits — live in configuration, not in a service.
ARC-5Exactly one place turns an exception into a response body.

Configuration

Edited by an admin, read by the app

Everything GET /config returns is data, not code: branding, theme tokens, the sign-in methods, the country dial codes, the document checklist, the ID dropdown and which image tiles each ID type asks for. An admin edits it; the app renders whatever it is given.

The app decides nothing. It does not know that a birth certificate has one side and an Aadhaar card has two, that Apple sign-in is switched off, or that seven images are needed. Every one of those is a value it receives. That is what makes the configuration editable at all — the moment the app hard-codes one of them, editing it server-side stops working.

6.1How it is stored

The service depends on a ConfigSource interface, never on where the values live. Today that is a validated JSON file; a database row replaces it without touching a service, a controller, or the response the app receives.

// container.ts — the whole migration
- const configSource = new JsonFileConfigSource(env.CONFIG_FILE);
+ const configSource = new DatabaseConfigSource(db);

6.2Every edit is validated first

One schema guards every way configuration can arrive — a file at boot, a database row, or an admin form. A bad edit is refused rather than reaching drivers, and every problem is reported at once because someone fixing a form wants the whole list:

ConfigInvalidError: Configuration is not usable:
  theme.colors.accent: Use a six-digit hex colour, e.g. #6E9179
  documents.documents.0.typeOptions.0.images: A type needs at least one image slot
  signIn.countries: Exactly one country must be the default, found 2
  features.emailSignIn: Remove "email" from signIn.methods, or switch emailSignIn on
IDRequirement
CFGA-1Configuration is validated against one schema before it is stored, whatever wrote it.
CFGA-2Every problem is reported together, keyed by the path that is wrong.
CFGA-3A choice a driver can select must be completable: an ID type with no image slots is refused.
CFGA-4The default sign-in method must be one that is offered, and exactly one country is the default.
CFGA-5A method listed for sign-in cannot also be switched off in features.
CFGA-6Ids are immutable once a driver record references them. Labels, order and image slots stay editable.
CFGA-7Each revision carries a version and a timestamp, so a client can tell one from another and a bad save can be rolled back.
CFGA-8A rejected edit leaves the previous configuration serving.

6.3What an admin may change

Freely editableEditable with careNot editable
Copy, colours, corner radii, fonts, support details, feature flags, country list, minimum age, code length and expiry, document labels and image slots, dropdown options and their order Removing a country or an ID type that drivers have already used, and the total step count, which the app's progress bar follows Document names and type ids once stored against a driver — renaming aadhaarCard after five hundred drivers have chosen it orphans their records

6.4Still to settle

The response is cached for five minutes, so an edit takes up to that long to reach a running app and longer for one that does not relaunch. A flag that must flip instantly needs either a shorter cache or its own uncached call. Endpoints for an admin to read and write configuration are not built.

Cross-cutting requirements

9.1Response shape

One success shape and one error shape, on every endpoint without exception.

{ "ok": true,  "data": { … } }

{ "ok": false, "error": {
    "code": "APPLICATION_INCOMPLETE",     // stable, safe to switch on
    "message": "2 items are still required.",  // safe to show a driver
    "fields": { "email": "Already in use" }  // maps onto form inputs
} }

9.2Authentication

IDRequirement
SEC-1Driver calls carry a bearer token; admin calls carry a separate key. Neither credential opens the other's surface.
SEC-2A refresh token is not accepted where an access token belongs.
SEC-3The driver id comes from the token, never from a request body, so one driver cannot act as another.
SEC-4A short-lived access token with a refresh path. POST /refresh trades a refresh token for a new pair, so the app renews in the background rather than sending the driver back to sign-in. Tokens are self-contained, so a refresh token cannot be revoked before it expires — a store is needed for that
SEC-5Code requests are rate limited per number and per address.
SEC-6Document file URLs never appear in a driver-facing response.

9.3Behaviour

IDRequirement
GEN-1A response carries only what a screen uses. No field is returned because it happened to be nearby.
GEN-2Completeness is computed on read, never stored, so counters cannot drift from the rows behind them.
GEN-3Mutating calls accept an idempotency key. Repeating one is safe.
GEN-4No third-party call runs inside a request. Anything slower answers with a poll target.
GEN-5Every message shown to a driver is written by the server, and none exposes an internal identifier.
GEN-6Endpoints are versioned before the app ships.

Out of scope

Named here so nobody assumes otherwise:

  • The driver app and the admin panel. This is a backend; it renders nothing.
  • Everything after approval — going online, accepting trips, earnings, ratings.
  • Rider-facing anything.
  • Payments, pricing and payout runs. Only the driver's payout setup is in scope, once a provider is chosen.
  • Push notification delivery. The trigger points are in scope; the transport is not designed.

Requirements are written from the screens rather than from an endpoint list, and each endpoint is designed only once the screen it serves has been reviewed. Anything marked assumed is a value we chose to keep moving — correct it and the code follows.
